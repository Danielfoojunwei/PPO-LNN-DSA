# Benchmark protocol

The pre-registered design, the statistical protocol, the seeding contract, and the recipe
for verifying any number this repository publishes.

**Scope.** This is the research-facing protocol: what was declared, what was run, how it is
analysed, and how a reader checks it. [`PROTOCOL.md`](PROTOCOL.md) is the *implementation*
contract the code is written against — internals of the environment, the learner and the
analysis layer — and [`MODEL_CARDS.md`](MODEL_CARDS.md) documents each cell against its
unit tests. Where any of these documents appears to disagree with the artifacts,
`results/manifest.json` and the CSVs under `results/` are authoritative.

**This document states no measurements.** Results live in [`../RESULTS.md`](../RESULTS.md),
which is generated by `scripts/make_report.py` from `results/`.

---

## 1. The question, and the shape of an answer

Liquid Time-constant networks and Closed-form Continuous-time networks are motivated by
*irregularly sampled* dynamics: their state update is a function of the elapsed interval
`dt`, not merely of the step index. Dynamic spectrum access under bursty, irregular decision
timing is a natural place to test that motivation.

The benchmark is built so the motivating claim can **fail**. Three design choices do that
work:

1. **A one-factor control.** `ppo_cfc_dtblind` is `ppo_cfc` with `dt` pinned to a constant
   inside the cell and nowhere else. Same architecture, same parameter count, same
   initialisation distribution, same encoder input (both arms still receive `dt` as a
   feature), same environment stream. Any difference between them is attributable to one
   factor: whether `dt` enters the recurrent state update.
2. **Capacity matching.** Every model is exactly two blocks deep and its hidden width is
   *solved* against a common parameter target, so a win cannot be a capacity artifact. In
   the previous version of this repository the largest model had more than twice the
   parameters of the smallest and parameter count correlated strongly with reward.
3. **Competitive zero-parameter baselines** in every table, with no filter anywhere in the
   analysis layer. If a hand-written heuristic wins, the tables say so.

## 2. Pre-registration

`configs/preregistration.yaml` is written before any confirmatory run and its sha256 is
recorded in `results/manifest.json` (`preregistration_sha256`). It declares the primary
comparison, the families, the correction, the metric and the direction. `scripts/analyze.py`
reads it; the families are not reconstructed after the fact.

### 2.1 The primary comparison, P1

> Does letting the elapsed decision interval enter the recurrent state update improve
> dynamic spectrum access under irregular decision intervals?

| field | value |
|---|---|
| arm A | `ppo_cfc` (`dt` enters the CfC time gate) |
| arm B | `ppo_cfc_dtblind` (architecturally identical, `dt` pinned inside the cell) |
| scenario | `irregular_dt` |
| metric | `mean_eval_return` (mean undiscounted episode return, greedy policy, shared eval stream) |
| test | two-sided paired exact sign-flip |
| correction | none — pre-registered singleton family F1 |
| direction | two-sided |

P1 is primary because it is the only comparison in the repository whose two arms are
identical in every respect except the factor under study. It is reported first in
`RESULTS.md` whatever its outcome.

### 2.2 Families

Multiplicity is controlled by Holm–Bonferroni **within** each declared family at
`alpha = 0.05`. Family membership is fixed in advance; nothing is regrouped after seeing
results.

| family | contrast | comparisons |
|---|---|---|
| F1 primary | P1 | 1 |
| F2 continuous vs gated | `ppo_ltc`, `ppo_cfc`, `ppo_ltc_cfc` vs `ppo_gru`, per scenario | 15 |
| F3 hybrid decomposition | `ppo_ltc_cfc` vs `ppo_ltc` and vs `ppo_cfc`, per scenario | 10 |
| F4 `dt`-awareness | `ppo_cfc` vs `ppo_cfc_dtblind`, per scenario | 5 |
| F5 learning check | trained vs untrained, per model per scenario | 35 |
| F6 vs greedy baseline | each PPO model vs `greedy_heuristic`, per scenario | 35 |
| F7 federated | the three topology arms, pairwise | 3 |

**The F6 baseline is fixed in advance.** It is always `greedy_heuristic`, never "the best
baseline in that scenario" — choosing the comparator after seeing the data is a selection
bias, and it is the specific move that made the previous version's tables look favourable.
`random_policy` and `constant_channel` appear as rows with intervals in every table but are
not part of a tested family.

### 2.3 Exploratory, and excluded from every family

`ppo_lstm` (a near-duplicate control of `ppo_gru`), and the scenarios `noisy_partial` and
`bursty_load`. They are registered, capacity-matched, unit-tested and runnable via CLI
flags. They were dropped from the confirmatory matrix to buy statistical power at 12 seeds
rather than breadth at fewer. No claim rests on them, and they carry no adjusted p-values.

## 3. The matrix

Declared in `configs/suite.yaml` and `configs/federated.yaml` — the only places the matrix
exists — and echoed into `results/manifest.json` at run time.

| dimension | confirmatory value |
|---|---|
| scenarios | `stationary`, `non_stationary`, `interference_heavy`, `irregular_dt`, `bursty_irregular` |
| models | `ppo_mlp`, `ppo_gru`, `ppo_transformer`, `ppo_ltc`, `ppo_cfc`, `ppo_cfc_dtblind`, `ppo_ltc_cfc` |
| baselines | `random_policy`, `constant_channel`, `greedy_heuristic` |
| seeds | `7, 19, 23, 41, 89, 101, 137, 211, 307, 401, 499, 601` |
| cells | `5 x 12 x 10 = 600` |
| training steps per cell | `10240` environment steps, `240` gradient updates |
| evaluation | `32` episodes per cell, shared stream, greedy policy |
| federated | 3 arms x 12 seeds, `36864` env steps per arm, model `ppo_ltc_cfc`, scenario `non_stationary` |

**Twelve seeds, not ten.** With `n = 12` the exact sign-flip test's p-value floor is
`2 / 2^12`, which survives Holm correction in a family of up to about a hundred
comparisons; at `n = 10` the floor is `2 / 2^10` and survives a family of only about
twenty-five. Seeds buy the ability to reject; that is why breadth (two scenarios and one
model) was cut instead.

### 3.1 Scenario semantics

Five dynamics classes, each fully specified in the frozen `ScenarioConfig` registry — there
is no post-construction mutation of a config.

| scenario | `dt` | drift | regime switching | interference | background load |
|---|---|---|---|---|---|
| `stationary` | constant | none | none | nominal | fixed |
| `non_stationary` | constant | yes | yes | nominal | fixed |
| `interference_heavy` | constant | mild | yes | elevated | fixed, higher |
| `irregular_dt` | log-uniform | none | none | nominal | fixed |
| `bursty_irregular` | bimodal | yes | yes | elevated | birth–death |

`irregular_dt` differs from `stationary` in **exactly one field**, `dt_mode`. That makes the
primary comparison an interaction test against a clean control, and it makes the F4 result
on `stationary` interpretable: on a scenario where `dt` never varies, the two arms are
identical in expectation, so whatever magnitude appears there is a direct read-out of the
noise floor.

`dt` genuinely varies in 2 of the 5 confirmatory scenarios. In the previous version, 6 of 7
scenarios reported a constant `dt` with minimum equal to maximum, which left the
continuous-time premise essentially untested. Two of the old "scenarios" were also the same
dynamics class with a different constant background-user count, so there were 5 classes
presented as 7.

### 3.2 Timing bookkeeping

One `dt` per transition, sampled once, used by every consumer: it advances the simulated
clock, drives the channel relaxation, drives the load birth–death process, and is what the
recurrent cell receives. `env.sim_time` equals the exact sum of the reported intervals, and
a unit test asserts that to float equality. The previous implementation advanced the clock
with the old interval while relaxing the channels with the newly sampled one, and passed the
new one to the cell — an off-by-one that made the `dt` a policy saw inconsistent with the
`dt` the world used.

## 4. The seeding contract

The highest-value guarantee in the repository. Every paired statistic below depends on it.

### 4.1 Derivation

Seeds are `blake2b(base_seed, role, indices...)` — a pure function of its arguments.
`blake2b` and not Python's `hash()`, which is salted per process for strings and would
silently differ between a parent and its worker. There are no mutable class-level counters
and no module-level mutable state; `SpectrumEnv` takes its episode seed as an explicit
constructor argument.

### 4.2 The rule that makes comparisons comparisons

**Environment seeds exclude the model name.** Training-lane and evaluation-episode seeds are
derived from `(base_seed, scenario, role, index)` only. Every policy in a given
`(scenario, seed)` cell therefore observes a byte-identical environment stream, which is
what licenses pairing differences by seed and what makes the resulting intervals tight.
Policy initialisation, action sampling, minibatch shuffling and heuristic RNGs *do* include
the model key, because those are properties of the arm rather than of the world.

### 4.3 What this replaced

The previous environment used a class-level `_instance_counter` and
`base_seed = config.seed + instance_id`, while the runner constructed a fresh environment
per episode in one process. A model's environment stream was therefore a function of its
position in the `--models` list. Measured with a *fixed* policy at one nominal seed, six
consecutive instances spanned roughly forty reward points, against a headline effect of
about two. Re-running the documented command moved the flagship model from first to sixth of
seven.

### 4.4 How determinism is enforced

- Every wall-clock column in every CSV is prefixed `wall_`, and **no other column may be
  non-deterministic**. The reproducibility tests drop exactly `^wall_` and require bitwise
  equality on the rest.
- `tests/test_seeding.py::test_env_stream_order_independence` digests full episode streams
  under two opposite model/scenario orderings with decoy environments constructed in
  between, and requires the digests to match.
- `tests/test_seeding.py::test_global_rng_is_not_load_bearing` perturbs the `numpy`, `random`
  and `torch` global RNGs between two identical runs and requires byte-identical metrics.
- CI runs the suite twice at the smoke budget with `--models` in opposite orders and diffs
  the outputs.
- The confirmatory evidence was additionally spot-checked: four cells were run in a
  two-model invocation, in a differently-ordered four-model invocation, and inside the full
  600-cell run, and agreed on every non-`wall_` column exactly.

## 5. The learner contract

Full detail in [`PROTOCOL.md`](PROTOCOL.md); the parts that bear on interpreting results:

- **True recurrence.** Hidden state is carried across environment steps. The fixed
  observation frame-stack of the previous version is gone. A stateless encoder over a frame
  stack cannot test a claim about continuous-time state evolution, because the state would
  be re-initialised at every decision — the previous version called that "Recurrent PPO".
- **The update recomputes the hidden trajectory** from the stored initial state for every
  minibatch. Stored per-step hidden states are never fed back in. Minibatching is over the
  sequence axis and is reachable by construction.
- **Dropout is zero everywhere**, and `.eval()` / `.train()` are used correctly: evaluation
  mode throughout rollout and evaluation, training mode inside the update. In the previous
  version neither method appeared anywhere in the live path, and dropout masks differing
  between rollout and update consumed a large fraction of the PPO trust region.
- **The ratio-sanity invariant.** On the first epoch of the first minibatch the importance
  ratio must be one, because nothing has been updated yet. Every run records
  `max_first_epoch_ratio_deviation`; the analysis fails the report if any run exceeds a
  strict bound. This single check catches stale hidden states, dropout mismatch and
  mode bugs simultaneously, and it is the reason a null result here can be attributed to the
  budget rather than to the update.
- **Real step counts.** `train_steps` is `agent.total_env_steps`, incremented by the vector
  width per step. The previous version recorded a declared figure that was six times smaller
  than the steps actually executed.

## 6. Statistical protocol

Implemented in `dsa/analysis/stats.py` in numpy. `scipy` is not a dependency — the previous
`requirements.txt` pinned it, it was not installed, and nothing imported it.

**Unit of analysis.** One `(scenario, model, seed)` cell yields one scalar: the mean
undiscounted episode return over the shared evaluation episodes under the greedy policy.

**Pairing.** Comparisons are paired by seed. Because environment seeds exclude the model
name (§4.2), both arms of any comparison saw byte-identical environment streams, so the
paired difference removes the environment as a variance source. `n_pairs = 12`.

**Interval.** Percentile bootstrap over the 12 paired differences, 20,000 draws, from a
generator seeded by `derive_seed(ANALYSIS_SEED, "boot", comparison_id)`. Deterministic
across runs and across machines: re-running the analysis reproduces the interval exactly.

**Test.** Two-sided paired sign-flip permutation test on the differences. For `n <= 20` all
`2^n` sign vectors are **enumerated exactly** — at `n = 12` that is 4096 evaluations and
takes microseconds — so there is no Monte-Carlo error and no RNG in the p-value. The floor
is `2 / 2^n`, never zero, following Phipson and Smyth. Larger samples fall back to seeded
Monte-Carlo; the method used is recorded per row in `p_method`.

**Effect size.** Cliff's delta accompanies every comparison, with the conventional
negligible/small/medium/large thresholds. A delta of `-1` or `+1` means one arm won at every
single seed.

**Correction.** Holm–Bonferroni within family. `holm_adjusted_p` and `significant` are
columns of `results/tables/comparisons.csv`, alongside the raw p, so anyone preferring a
different correction can apply it to the raw values.

**Reporting rules, applied mechanically.**

- Every difference is reported with `n`, both arm means, the mean difference, a 95%
  interval, raw p, method, family and adjusted p.
- Numbers are formatted to three decimals. The previous version reported ablation gains to
  seventeen significant digits with no uncertainty column, in a table where most gains were
  smaller than the baseline's own across-seed standard deviation.
- **Any comparison whose interval contains zero is described as "no detectable difference",
  never as a gain.** Where an interval marginally excludes zero but the pre-registered test
  does not reject after correction, the test governs and no difference is claimed.
- Baselines appear as rows in every table. `tests/test_no_filter.py` fails the build if any
  file under `dsa/analysis/` or `scripts/` contains a hardcoded model list used as a filter.

## 7. The learning check

Every training run is evaluated **twice on the identical evaluation stream**: once with
freshly initialised weights, once after training. Both go into `results/all_runs.csv` as
`mean_eval_return_untrained` and `mean_eval_return_trained`, and family F5 tests the paired
difference.

This exists because the previous version's entire budget amounted to 72 full-batch gradient
steps and a controlled test showed its models performing no better than their
initialisations — a fact its documentation never surfaced because it never measured it. If a
model does not beat its own initialisation here, `RESULTS.md` says so in the same font as
everything else.

## 8. Federated protocol

**Three arms, strictly compute-matched.** Each executes the same number of environment
steps, and every runner reports both the summed real step count and the declared figure;
`tests/test_federated.py::test_train_steps_equals_reality` fails if they differ.

- `centralized` — one agent on a pooled client distribution. Transmits no parameters. A
  performance reference, not a communication baseline.
- `flat_federated` — every client initialises from the cloud model and aggregates directly
  at the cloud.
- `hierarchical_federated` — clients initialise from **their edge**, edge-local FedAvg runs
  for several inner rounds and the edge state **persists** across them, and only edge models
  reach the cloud. In the previous implementation clients were seeded from the global model
  and the edge state was computed and then discarded, making the hierarchy a no-op; a
  regression test now asserts the hierarchical result is *not* equal to flat FedAvg over the
  same clients.

**Client heterogeneity is clustered by edge**: clients on the same edge share drift and
interference parameters, which is what makes edge-local aggregation meaningful, with small
within-edge variation in background load only.

**Communication is measured, not derived.** Every transfer is recorded at the moment it
happens and its size is `sum(t.numel() * t.element_size())` over the actual payload tensors.
Three columns are reported for every arm — wide-area (cloud), edge-local, and total — because
the honest statement about hierarchy is a trade-off, not a saving. The previous version
hand-computed byte counts in closed form, which produced a suspiciously exact ratio and a
zero standard deviation across seeds; a test now greps for arithmetic on parameter byte
counts outside the ledger.

## 9. Verifying any published number

Every number in `RESULTS.md` and in `README.md` carries a `claim_id`. `results/claims.json`
maps each id to its statement, source file, source column, value, interval, p-value,
adjusted p and verdict.

```bash
# What does a claim say, and where did it come from?
python - <<'PY'
import json
claims = {c["claim_id"]: c for c in json.load(open("results/claims.json"))["claims"]}
c = claims["CLAIM.PRIMARY.P1"]
print(c["statement"]); print(c["source_file"], "::", c["source_column"], "=", c["value"])
PY

# Are the committed tables and report actually derived from the committed CSVs?
make check          # analyze --check  +  make_report --check ; writes nothing
```

To re-derive the primary comparison without trusting the analysis layer at all: read
`results/all_runs.csv`, filter to `scenario == "irregular_dt"`, pivot
`mean_eval_return_trained` by seed for the two arms, difference them, and enumerate all
`2^12` sign vectors. The p-value is the fraction of sign assignments whose mean absolute
difference is at least the observed one.

Three gates keep this honest, and CI runs all of them:

1. `pytest -q` — the unit suite, including the seeding, no-filter and no-hardcoded-metric
   tests.
2. Order-invariance — the smoke suite run with `--models` in opposite orders must produce
   identical non-`wall_` columns.
3. `make check` — regenerated tables and `RESULTS.md` must be bit-identical to what is
   committed.

## 10. Known limits of this protocol

Stated here rather than left to a reader to discover; the results-specific version is in the
README's limitations section.

- `n = 12` per comparison. The exact test can detect a large consistent effect and cannot
  rule out a small one. Absence of a detectable effect is not evidence of absence of an
  effect.
- The pooled ranking is a mean of per-scenario means; its interval is over 5 scenarios and is
  descriptive only. No pairwise ranking claim is tested outside a declared family.
- Within-cell episode variance is not propagated into the family-level tests; the cell mean
  is the unit.
- 104 comparisons is a lot of comparisons. Holm within family is the pre-registered answer
  and it is conservative. Raw p-values are published so that a different correction can be
  applied without re-running anything.
- The confirmatory budget is small, and a null under a small budget is a statement about the
  budget as much as about the architectures. `results/all_runs.csv` publishes the learner
  diagnostics (`final_explained_variance`, `mean_policy_entropy_nats`,
  `total_gradient_steps`) precisely so that a reader can judge whether the learner reached a
  regime in which the comparison was informative.
